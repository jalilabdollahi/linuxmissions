# Module 13: Services and Logs

This module teaches running services with systemd (reading status, enable vs start, disable vs mask, reload vs restart, unit files, drop-ins, environment, restart policy, dependencies) and reading the logs that explain them (the journal, the kernel ring buffer, syslog, auth.log, nginx, application logs), ending with incident capstones that combine all of it. systemd and the journal aren't available to a non-root player (and not in Docker), so levels use a shared mock `systemctl`/`journalctl`/`systemd-analyze`/`timedatectl` that work on `$SANDBOX/etc/systemd`, `$SANDBOX/lib/systemd` and a JSON journal export. The mocks really start background processes from `ExecStart=` and create real wants and mask symlinks. How I handled overlaps: module 7 did a first enable/start and a first "grep the journal for error", and this module is the home for everything beyond that. Module 15 owns timers and scheduled logrotate; here logrotate is about a service keeping the old file open. Module 17 tracks journal errors and log noise over time; here the job is triage. Module 23 uses dmesg and the journal for boot and hardware failures; here dmesg explains a crashed service. Module 11 uses logs only as pipeline input and avoids nginx and auth.log. The `/proc` slugs are reframed around a service (proc-maps, proc-cpuinfo) or replaced, because cpu-info and mem-info are module 24's. `hostnamectl` is replaced because module 24 has hostname, and `localectl` because locale changes need root and leave nothing service-related to check.

## Notes

- One shared mock systemd toolkit (`systemctl`, `journalctl`, `systemd-analyze`, `timedatectl`) should extend module 7's helper. It must create real symlinks for enable/mask, start real background processes with the sandbox path in their command line (authoring rule 5), track `daemon-reload`, and support `show -p`, `cat`, `set-property`, `list-dependencies` and a `boot` simulation.
- Linux-only: level 15 (`/proc/<pid>/maps`; setup maps a file with `python3 -c 'import mmap…'` and then deletes it) and level 11 (`/proc/<pid>/fd`, and real logrotate, which is in the Dockerfile; macOS needs Homebrew logrotate).
- dmesg, the journal and `/proc/cpuinfo` are captures (levels 7, 16, 17, 23, 24), because `dmesg_restrict` and missing systemd in Docker make them unavailable to a non-root player.
- Level 12 relies on a background writer that waits for `trigger-deploy.sh`. The objective should mention that commands can be backgrounded with `&` and stopped with Ctrl-C in the game shell.
