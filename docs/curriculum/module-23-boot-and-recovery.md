# Boot and Recovery

This module teaches how to diagnose and repair a machine that won't boot, without ever rebooting anything. In almost every level the broken server is a captured root filesystem in `sysroot/`, as if its disk were mounted in a rescue system. The player works on real artefacts from it: `grub.cfg`, initramfs images, `fstab`, unit files, `modprobe.d`, the boot log, journal exports, ELF binaries with their libraries, and an ext4 image repaired with the real `e2fsck`. Where a real tool would need root or firmware (`update-grub`, `efibootmgr`, `modprobe`), setup ships a small mock that reads and writes files under `sysroot/`. A recurring lesson is that inside a rescue system, absolute paths and symlinks must be read as the *booted* machine will see them. Overlap decisions:
- Module 13 owns dmesg and journalctl basics. Here, dmesg-errors correlates hardware errors to a disk, and journal-boot works across several boots of an exported journal.
- Module 14 owns fstab review and snapshot or restore drills. Here those topics are used to fix a boot failure.
- Module 24 owns reading `uname` on the live box. Here uname-a means fleet-wide reboot detection.
- Module 12 owns the login files (`/etc/profile`, `.bashrc`) and account locks. Levels 22 and 23 use them as recovery puzzles.

## Notes
- Mocks shipped by setup: `update-grub` (writes `grub.cfg` from `default/grub` and `grub.d/*.cfg`, with a checksum stamp), `modprobe-sim` (reads `modules.dep` and `modprobe.d/*.conf`), `efibootmgr` (keeps BootOrder in a state file), `fstab-lint`, `app --check-config`, and `login-sim` (copies the login files with `/etc` rewritten to `sysroot/etc` and runs `env -i bash --login`).
- The Dockerfile needs `cpio` for level 2 (module 10's cpio level needs it too). Check that `e2fsprogs` (`e2fsck`, `mke2fs`, `debugfs`) is in the image for level 5, and add it if not. setup.sh damages the image with `debugfs -w`, which works on a regular file without root.
- Linux-only: level 5 (e2fsprogs), level 21 (`ldd`, `dpkg-deb`; setup must find the multiarch lib directory, x86_64 or aarch64, from the host's `ldd` output), and level 2's zstd image.
- Levels 1, 14, 24 and wargame 28 all parse `grub.cfg`. Generate them from one shared fixture generator so the format stays consistent.
